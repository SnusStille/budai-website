## 2. Root-Cause Diagnosis of the Post-Playground / Capabilities Scroll Flicker & Jump

Through code auditing and automated browser instrumentation across the `#signal` → `#playground` → `#capabilities` → `#about` scroll boundary, we identified **three concrete root causes** of the ~1-second scroll flicker/jump and fixed each at the architectural level:

1. **Root Cause 1 — Vertical Camera Frustum Reversal via `camera.setViewOffset` Chasing `getBoundingClientRect().top` (`lib/experience/world.ts`)**:
   - *Mechanism*: Previously, `world.ts` measured `capViewport.getBoundingClientRect()` and `accessViewport.getBoundingClientRect()` every frame, interpolated `targetRect.top = lerp(engineRect.top, accessRect.top, morph)`, and passed that pixel offset into `camera.setViewOffset(...)`.
   - *Why it jumped*: When scrolling down from `#playground` into `#capabilities` before `.capability-sticky` pinned at `top: 95px`, `engineRect.top` swept rapidly from `+950px` to `+95px`. Worse, as the user scrolled from `.capability-sticky` into `[data-access-architecture]` (`Choose your way in`), `engineRect.top` scrolled off the top of the screen (`-120px`) while `accessRect.top` entered from the bottom (`+640px`). Interpolating `lerp(-120, +640, morph)` forced the 3D camera frustum to **reverse direction and jump ~760px vertically** while the user was scrolling steadily downward, simultaneously rescaling `engine.root.scale`!
   - *Fix*: Eliminated `getBoundingClientRect().top` from `camera.setViewOffset` and `engine.root.scale`. The Capabilities 3D Studio is now anchored at a fixed world coordinate inside `capabilities` (`(48, -0.35, -28.85)`) with deterministic viewport-ratio framing (`offsetX = lerp(-frame.width * 0.165, 0, morph) * capWeight`, `offsetY = lerp(-frame.height * 0.015, -frame.height * 0.035, morph) * capWeight`). The camera frustum never chases scrolling DOM `top` coordinates and never reverses direction.

2. **Root Cause 2 — 30fps RAF Throttling During Active Native Scroll (`lib/experience/scroll.ts`)**:
   - *Mechanism*: In `lib/experience/scroll.ts`, when `continuous` mode was active (while `.universe-world` was visible), `raf = requestAnimationFrame(frame)` was queued at the end of every tick. When a native `scroll` event fired, `schedule()` saw `if (raf || disposed) return;` and did nothing, while `frame()` gated updates behind `if (now - last >= 30 || !last)`.
   - *Why it flickered*: Native browser scroll runs at `60Hz` (`16.6ms`) or `120Hz` (`8.3ms`), whereas `world.update(frame)` was skipping every second or third scroll frame (`30ms` throttle), causing visible judder between `position: sticky` DOM elements and the `position: fixed` 3D canvas.
   - *Fix*: Added an explicit `scrolling` flag in `lib/experience/scroll.ts` (`onScroll` sets `scrolling = true`). Whenever the user is actively scrolling or resizing, `frame()` executes all journey subscribers at **1:1 native RAF cadence (60Hz/120Hz)**, while idle ambient animation remains capped at `30fps` to save battery and GPU resources.

3. **Root Cause 3 — Mid-Token Syntax Color Flipping During Progressive Code Typing (`components/experience/CapabilityMap.tsx`)**:
   - *Mechanism*: `CapabilityMap.tsx` previously sliced each code string first (`line.slice(0, remainingChars)`) and called `tokenizeLine(partialLine)` on the incomplete string. While typing a string literal (e.g., `'sv-SE'`), before the closing quote appeared, the regex tokenizer classified the partial token as `plain` (white), then abruptly flipped the entire word to `string` (mint green) on the frame the closing quote arrived.
   - *Fix*: Applied Builder's exact `ProgressiveEditor.tsx` pre-tokenization architecture to both `CapabilityStudioScreen.tsx` and `CapabilityMap.tsx`: each full line is tokenized once via `useMemo`, and progressive typing slices `token.text.slice(0, take)` per token so syntax colors never flicker.

## 3. Unified Builder-Benchmark 3D Capabilities Architecture (`CapabilityStudioScreen.tsx` + `capability-engine.ts`)

Using the **Builder (`#about`)** section as our quality benchmark, we identified why Builder feels genuinely three-dimensional and convincing:
- It projects a **real vector DOM surface (`1080×605`)** via `CSS3DRenderer` (`CSS3DObject`) onto a physical 3D monitor (`RoundedBoxGeometry` brushed-alloy bezel, graphite stand, slatted architectural back wall, and real `PointLight` illumination), flanked by angled 3D side monitors with mipmapped `1024×512` `CanvasTexture`s.

We applied this exact architecture to `#capabilities` so **Act I (`The Infinite Code Chamber`)** and **Act II (`AI Assembly Line`)** are no longer two separate, disconnected animations, but **one continuous 3D Synthesis Studio** (`lib/experience/capability-engine.ts` + `components/experience/CapabilityStudioScreen.tsx`):
- **Real `CSS3DObject` Central Studio Monolith (`<CapabilityStudioScreen />`)**: Portaled via `WorldStage.tsx` (`world-capability-mount`) onto the central `6.5m × 3.64m` 3D studio monitor in `#capabilities`.
  - **Left Pane (`55%`)**: Builder-grade progressive TypeScript code editor with line numbers `01..10`, active-line highlight, blinking cursor, and pre-tokenized syntax highlighting.
  - **Right Pane (`45%`)**: Live-materializing BudAI UI component & telemetry preview directly synthesized from the code on the left.
- **Continuous Scroll Evolution (Act I → Act II)**:
  - **Act I — Capability Synthesis (`01 Write` .. `06 Vision & Voice`, `morph < 0.48`)**: The studio frames the right column beside the 6 interactive capability cards. Scrolling through modules `01..06` (or hovering any module) progressively types that module's TypeScript source (`01-write.ts` .. `06-multimodal.ts`), constructs its corresponding UI component (`Proposal Composer`, `Playbook Pipeline`, `Decision Matrix`, `SV / EN Bridge`, `RLS Context Vault`, `Vision & Voice`), illuminates the corresponding physical 3D pedestal node along the studio desk rail, and updates the left/right flanking 3D displays.
  - **Act II — Connected 3-Tier System Pipeline (`Choose your way in`, `morph >= 0.48`)**: As the user scrolls down into `[data-access-architecture]`, **the same 3D studio workstation smoothly centers across the viewport and articulates**:
    - The left physical 3D wing monitor rotates outward into **`01 · MULTIMODAL INTAKE (BASIC)`** (live Chat, Vision AST, and Voice signals).
    - The central `CSS3DObject` Studio Screen transitions to **`pipeline-synthesis.ts`** + the **Connected 3-Stage Pipeline (`01 Basic → 02 Consumer → 03 Business`)**.
    - The right physical 3D wing monitor articulates into **`03 · TEAM WORKSPACE (BUSINESS)`** (live velocity telemetry and verified enterprise metrics).
    - All 6 physical 3D desk nodes and the emerald waveguide bus bar illuminate in unison to carry the signal from Basic intake to Business team output.
